# 载具履带、材质与乘员视角运行审查

本轮使用用户指定的实际实例 `D:\无bug\.minecraft\versions\1.21.1-NeoForge_21.1.265\`。初始安装为 VLS 1.0.0m、Radar 1.14.1、Loadout 1.2.1、Superb Warfare 0.8.9.1，NeoForge 21.1.265；不是昨天的开发客户端组合。原 mod 在工作区备份，原有存档没有作为测试对象。

## 源码与安装包

用户提供的 `D:\WorkBuddyProjects\zzy\gitwork\sbw-vls` 包含 DeepSeek 的武器接线、无武器 HUD 和座位引用修复。实际 1.0.0m 安装包的 281 份载具定义与该源码逐项一致，未发现无效的座位武器引用。保留这些修复。

随后核对 GitHub 主线，上传的同组三个提交使用了不同提交 ID；22 个 JSON 的排版不同，解析后的内容一致。本次修复分支基于云端 `3ff0e77`，没有用旧副本覆盖这组修复。

## 已定位的问题

| 问题 | 原因与处理 |
| --- | --- |
| Abrams-X 等履带伸向空中 | 原车型的履带路径函数、节距和循环周期未随通用实体/渲染器一起移植。通用默认 Y/Z 位移直接返回相位值，不能形成闭合履带。恢复 39 型、38 套原曲线；每个实体使用自身循环长度，不能全部固定为 100。 |
| 原 Rail Tank 特定相位坐标无效 | 原曲线有两处除以零，按该段起止关键帧时刻修正分母；同时修正一段明显写错的角度时间区间。 |
| 原 Abrams-X 循环末端角度跳变 | 原最后一段角度插值分母与起止时刻不符，造成约 13.3° 接缝，按该段实际时长修正。 |
| Bradley / Oplot / T-72B3M 剩余装配错位 | SBM 运行时使用父节点局部绑定平移，基类履带代码却写模型空间枢轴。修正 `bind - pivot` 差值；基类后坐代码还把 `base.x/z` 写成从零开始的偏移，现保留其绑定平移。T-72B3M 的实机复验已恢复车体、轮系与履带对齐。 |
| 开镜被自身炮管/装甲遮挡 | 恢复原车型隐藏标志还不够：CV90 等模型存在多根骨骼，基类只隐藏名为 `root` 的节点。改为本地乘员开镜时跳过本车外观绘制，普通外观与其他车辆绘制不变；高精路径同样处理。 |

| 28 份灰色占位贴图 | 从 FCP 原实体/渲染类的默认贴图声明找回原 PNG，逐字节保留；HMMWV 各附件版本使用原 `HumveeUnarmedEntity` 声明的同一套默认车体 UV。没有靠缩小贴图或重新涂色掩盖问题。 |
| 19 款 VVP 载具无效弹药物品 | `vvp:item_30mm`、`vvp:ap_shell` 在实际实例未注册，替换为 SBW 小口径/大口径穿甲弹物品；投射物、伤害、速度和装填参数不变。 |
| 20 种遗留图标路径失效 | Halo 原图找回；AH-64、Humvee、23mm、AAM 对应原图重定位；旧 SBW 路径修正或明示替换为现有同类图标。IRIS-SLM 的武器图标紫黑块属于此问题。 |

## 验证方法与当前状态

- 全部 281 份模型索引：最终构建中 `Models` 非空，直接模型/贴图引用存在。
- 39 型履带：每型 10001 个相位扫描，位置和角度有限；所有路径首尾位置一致。保留原关键帧造型，少数原采样表仍有约 1–2.5° 的旋转末端差异，未把它说成所有曲率完全平滑。
- 原整合包中已手动复现 Abrams-X 履带拉伸，并保存 F2 截图。四型修复前对照为 Abrams-X、BMP-2、T-90MSA、M3A3。
- 临时 QA 组件在实际 `mods` 目录加载，自动创建独立审查世界；输出三个履带相位外观、驾驶 HUD、炮手开镜和前向输入驱动状态。原生开镜处理函数发送正常的 ZoomMessage，日志确认 `zoomVehicle` 状态；炮手与驾驶员不同座位的车型分别切换正确座位。
- 驾驶阶段使用原生前向输入标志与实际物理，记录位移及能量；位移为零时不能据此声称实驾通过。外观相位检查本身也不等于实驾检查。
- 第一轮 54 型取图 324 张，随后 63 型复验取图 378 张；63 型日志中开镜状态均成功触发、前向输入均有实际位移、未报缺失几何。人工看图仍找出了多根骨骼遮挡、图标紫黑块，因此这些日志不被当作视觉全部通过的依据。最终外观全量和开镜补查结果见交付验证清单。

临时 QA 的类不打入生产 VLS JAR。测试结束后从 `mods` 移除临时组件。

## 范围限制

本轮区分资源、外观动画、视角和物理问题。恢复多材质绘制不等于给所有原本静态的 WT 部件重新绑定炮塔、炮管、雷达及发射架；这些部件的完整运动仍需逐项检查。WT 原始材质中仍有单色 PNG，恢复原材质不能凭空恢复缺失的迷彩。

全量截图还确认 `ural4320 / ural4320_supply / ural4320_zu23` 存在原始材质缺陷：轮胎、篷布等新增块面的 UV 指向例如 `(149,360)` 的全透明像素，原附属包对应 PNG 也相同，因此恢复原 PNG 并不能恢复这些部件。驾驶室本体存在；侧面看似只剩车架主要是透明材质所致。这三款尚未修复，不能计作完整外观通过。需要找回带颜色调色板的正确纹理/编辑源，而不是随意借另一辆 Ural 的贴图。

`test` 是两个大立方体的占位条目，`test_ship` 的原几何实际为直升机；均为原包遗留测试定义，不作为完成的船只模型认定。本轮保留 ID，避免擅自破坏存档，但明确列为待处理内容。

部分飞机的嵌套弹药覆盖仍引用 `dragonrise_reforge` 的 AIM-120、AGM-65、JDAM-ER、GBU-24、KD-88A、GB250、LS6、LS6-IR、GBU-12 实体；实际实例未注册。没有把这些制导武器直接替换成无制导炸弹，本轮也未验证全部射击/制导逻辑。外部声音和部分弹种显示名仍需专门适配。`ray` 是上游有效特殊投射物标记，不列为丢失实体。挂架适配继续暂停。

## 复现与构建

`tools/restore_track_profiles.py` 从用户原附属的曲线反编译结果生成纯数值 `TrackProfiles.java`，不执行旧实体类。原输入来自用户桌面的原附属 JAR 及 FCP 备份；中间结果在 `local/review-20261031`，不入库。数值代码已随源码提供，普通构建不要求重新反编译。

`tools/restore_display_resources.py` 恢复原 PNG 并重写引用，`tools/restore_high_detail_indices.py` 为九型生成轻量索引。恢复的美术资源按仓库既有规则随完整 Release 提供，不直接进 Git。

构建基于固定 SHA256 的完整 `local/input-1.0.0m.jar`；先准备恢复后的美术资源，再执行 `python tools/build_release.py`、`python tools/audit_release.py`。全部 281 份权威数据均进入产物，不再仅在存在 `Loadout` 字段时覆盖输入数据，以免以后丢失座位/HUD 修复。构建输入不会被修改。
