## 保留模型的检查与修复

原包实际有 61 台飞行器（33 Airplane / 28 Helicopter）。逐机检查真实几何和模型索引：未发现缺失资源、重复骨骼、缺失父骨骼、循环父链、空几何或非有限坐标。用递归骨骼绑定变换绘制俯视/侧视检查图；不以实体核心 AABB 等同整机尺寸，也不使用分位裁剪丢掉细长机翼。

发现 Huey 火箭版使用 64×64 单色灰占位图。追溯 FCP 原始实体的贴图列表，恢复其原始 `textures/entity/huey/huey_1.png`；保留原图字节、尺寸和模型几何。五款前机身按用户后续要求重新拓扑和平滑，其余模型未做几何简化。

旧报告把 AH-1F 静止状态的双叶旋翼纵向排布列为可疑；仅凭这个静止方向不能断言建模错误，此次没有据此旋转或重做桨叶。动态行为需结合实际渲染核对。

清理后保留 **281 份载具数据定义、60 台飞行器（32 Airplane / 28 Helicopter）**。JSON 的类型有沿用旧分类的情况，例如 ac130 被原作者注册为 Helicopter；这里的统计遵从实际包数据。

本版本交付二战模型清理、灰贴图修复、机头恢复与 Blender 平滑、Mi-17 朝向修正及 Buk-M3 注册修复。动态挂架仍在工作区校准与验证，未作为此版本已经完成的功能发布。

## 用户反馈后的真实游戏复查（2026-10-30）

首轮远景截图不足以证明细节正常。随后重新启动实际 Minecraft 客户端，保留 60 台飞行器的 front / side / rear / underside / nose_gear 五视角截图，共 300 张修复前近景。摄像机根据实际可见骨骼网格的变换结果取景，并独立于驾驶员相机；截图不使用离线模型图冒充游戏画面。

实测确认以下缺陷，之前的资源链和父链检查没有发现它们：

| 模型 | 缺陷 | 最终修复 |
| --- | --- | --- |
| F-15E | 前机身、雷达罩消失，恢复后台阶明显 | 重建 850 个受损材质体素的连续外壳，匹配原灰色 |
| F/A-18E | 前机身消失，首次修复选色过浅 | 重建 601 个受损材质体素，改用原机身主灰色 |
| J-16 | 前机身、机头消失，座舱与机身共用坏 UV | 重建 1653 个受损材质体素，空间划分透明座舱 |
| JAS 39E | 前机身消失 | 重建 459 个受损材质体素，匹配原深色涂装 |
| Su-24M | 机头消失，首次修复的白色与机身不匹配 | 重建 443 个受损材质体素，改用原灰色 |
| Mi-17 | yaw=0 时机尾朝 +Z，机头与驾驶席及飞行前向相反 | 增加完整视觉骨骼层级的固定 180° Y 轴对齐 |

前五项的几何本身存在，但相同受损机身材质共影响 **4006 个**立方体，全部采样到透明空白。仅修前段少量 UV 的首轮修复不足以形成连续机身，因此没有采用该中间结果。完整材质索引保存在 `tools/model_repairs.json`；`repair_models.py` 保留用于诊断复现，**最终版本采用下述 Blender 转换结果**，不可在转换后再次运行 UV 诊断修复而覆盖平滑模型。

按用户要求，在实际 Blender 5.2.2 LTS 中对这些体素外壳做 0.035 m Voxel Remesh、60 次平滑及一级 Catmull-Clark；导出原骨骼下的原生 SimpleBedrockModel `poly_mesh`。没有使用减面修改器。保留各模型其余立方体、骨骼、父链、枢轴、动画及所有载具 JSON；原始 PNG 字节完全不变。新壳体用原贴图内连续同色区域的中心像素匹配材质，避免采样边缘引入杂色。主色 RGB 分别为 F-15E 109/118/123、F/A-18E 151/161/168、J-16 132/137/143、JAS 39E 56/59/71、Su-24M 98/102/108。

J-16 的透明座舱按模型坐标单独划分，其他原有玻璃/座舱框保留。UV 导出遵从本机 SimpleBedrockModel 2.5.1.1 的原生 `poly_mesh` V 轴转换规则，并经过实际游戏验证。

转换后五个壳体共 **1,186,384 个三角面**。逐项验证三角索引有效、坐标有限、法线归一化且与面绕序一致、每条边恰有两个相邻面；除指定外壳以外，完整模型 JSON 与原包逐字段一致。各轴边界相对原壳体变化最大约 **8.1 cm**，不等于整个曲面的最大距离误差；碰撞、座席等物理数据仍为原值。这是提高曲面质量的重建，面数和资源占用增加，未做 FPS 基准测试。

Mi-17 的驾驶席 Z=+2.56、尾部碰撞箱 Z=-12.8，已使用原生 +Z 前向；问题在导入模型的视觉朝向。仅给视觉层级添加固定对齐父骨骼，保留驾驶、座席、相机、碰撞箱和飞行逻辑，原始立方体及 UV 均不变。复现脚本为 `tools/repair_orientation.py`。

Mi-17 同角度截图已确认机头朝向正确。五款 Blender 修复机各保留 front / side / rear / underside / nose_gear 五个同角度真实游戏截图，共 25 张；逐机查看机头、侧面、背面及底部，确认连续机头、机身主色衔接、座舱与保留部件显示。截图前缀 `blenderfinal_`，不使用早先摄像机调试或部分 UV 修补截图作为最终结果。该检查覆盖展示状态与起落架切换，不代表全部飞行、损毁、武器和动画已穷尽验证。

Blender 源文件含新外壳、原贴图、预览相机与灯光。其余部件的参考网格由游戏实际姿态导出，避免直接导入原始静态骨骼造成部件散开；参考网格只用于编辑对照，转换脚本仅输出指定外壳。

重新从源码构建时还发现 `VlsEntities.BUK_M3` 从未注册赋值，客户端却使用它注册高精渲染器，导致资源加载时出现 `null key in entry`。已补齐该实体的实际注册与工厂，保留原 ID `zzyvehicles:buk_m3`，避免仅跳过空值而让载具永久消失。

## 构建

输入包为 Releases 的完整 `1.0.0j`，放到 `local/input-1.0.0j.jar`，SHA256 必须为 `be27945c2217c0b879f95cfb83c24b5bd379af674e0d4c13d25e1ed8ae8006f7`。

1. `python tools/remove_ww2.py`，`python tools/repair_orientation.py`。
2. `python tools/prepare_blender_repairs.py`，需要 Python 的 Pillow / NumPy。
3. 用 Blender 5.2.2 LTS 为 `f15e fa18e j16 jas39e su24m` 分别执行：`blender --background --factory-startup --python tools/blender_smooth_airframes.py -- <工程绝对路径> <ID>`。
4. `python tools/audit_blender_repairs.py`。
5. `python tools/build_release.py`、`python tools/audit_release.py`。

交付的 Blender 源文件压缩包同时包含转换后的几何，可直接放到 `resources/assets/zzyvehicles/models/bedrock/vehicle/` 再构建。Java 21；编译类路径来自已解析的相邻 sbw_loadout 工程。构建重新编译本仓库全部生产 Java，按显式清单打包；不会修改原始工程、备份或输入包。`local/` 不入库。重建预览场景可在游戏 QA 导出 `*-game-context.json` 后，运行 `blender_game_context.py`；这一步不改变游戏模型。
